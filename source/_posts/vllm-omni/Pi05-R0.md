# Pi0.5 R0：单请求运行时优化

R0 在 Pi0.5 的功能实现上加入静态 buffer、CUDA Graph 和融合 kernel，以降低 BS=1 的请求延迟。它需要保留可比较的 eager 路径，并同时交付正确性测试与性能证据。[R0 issue #7754](https://github.com/vllm-project/vllm-omni/issues/7754)；[实现 PR #8202](https://github.com/vllm-project/vllm-omni/pull/8202)。

本文接续 [Pi0.5 roadmap](Pi05.md)，分为性能优化与数值精度两章。第一章按 R0 当前实现说明优化机制、取舍、伪代码、A/B 方法与性能结果；第二章从真实的 BF16 超差出发，研究误差定位、修复和回归验证。

## 一、性能优化

本章按 PR #8202 当前实现说明单请求提速：先看执行路径和优化取舍，再用伪代码展开，最后核对 A/B 方法与性能结果。实现对应 `fceed074`，具体测量配置随表说明。[PR 正文](https://github.com/vllm-project/vllm-omni/pull/8202)

> 数据说明：本章引用 PR 已有测量，未自行复测。公开数据主要展示组合收益和分区耗时，尚未完整拆分各优化机制及 Graph 拓扑的独立贡献；作者的取舍理由与已给出的测量结果分别呈现。

### 1. 优化目标与范围

F1 已完成 Pi0.5 的模型、预处理和服务接入。R0 在这个功能基线上降低 **BS=1、一次 observation 生成一个 action chunk** 的延迟，主要改变 KV 存储、计算提交方式和 kernel 组合，同时记录显存成本。

R0 仍由一次 `sample_actions` 完成全部 denoise step。模型层的三个 Graph region 是捕获边界，服务 scheduler 不会因此在每个去噪步重新调度请求。B>1 优化、continuous batching 和框架公共组件集成属于其他工作项。[R0 范围](https://github.com/vllm-project/vllm-omni/issues/7754)

本章关注 KV 拼接与分配、CPU 提交、算子间访存三类成本，最终用请求延迟和显存衡量收益。

### 2. 当前执行路径与实际优化点

#### 2.1 一次请求经过哪些计算

```text
observation → 预处理、输入张量
                    ↓
              prefix embedding                  每请求 1 次
                    ↓
          prefix mask / position 构造
                    ↓
              prefix forward                    每请求 1 次
                    │ 写入逐层 prefix K/V
                    ↓
     ┌─ 当前 latent、timestep
     │              ↓
     │         denoise_step → velocity           每请求 N 次
     │              ↓
     └──────── Euler 更新 latent
                    ↓
              action 后处理、返回
```

`denoise_step` 预测 velocity。Python 循环、每步 timestep 张量的生成以及 Euler 更新都在第三段 Graph 之外；timestep embedding 则在 `denoise_step` 内。[sample_actions](https://github.com/vllm-project/vllm-omni/blob/fceed074ae2f9828afa901149b2a925cf1cb0713/vllm_omni/diffusion/models/pi05/modeling_pi05.py#L1731)

#### 2.2 静态 KV：复用存储，原地覆盖 suffix

`Pi05KVCache` 的 key 和 value 各自使用以下布局：

```text
[num_layers, batch, num_kv_heads, prefix_len + suffix_len, head_dim]

每层 token 轴：
|      prefix 区域      |      suffix 区域      |
| 每个请求重新写入一次   | 每个 denoise step 覆盖 |
```

Pipeline 初始化模型后，按部署形状分配 BS=1 的 `model.kv_cache`。当前请求先写入自己的 prefix K/V，后续每一步用当前 latent 生成 suffix K/V，覆盖同一段 suffix 槽位。Attention 读取整层连续的 `[prefix | suffix]` 视图。

它减少的是每层、每步重新 `cat(prefix, suffix)` 所需的合并缓冲区及重复搬运 prefix。Suffix 保存当前步的内容，不会把历次 denoise 的 K/V 越积越长。存储可以跨请求使用，但每个请求仍重新计算并写入 prefix。[Pi05KVCache](https://github.com/vllm-project/vllm-omni/blob/fceed074ae2f9828afa901149b2a925cf1cb0713/vllm_omni/diffusion/models/pi05/modeling_pi05.py#L262)

**R0 自身的 eager 路径也使用这块预分配 KV。** Cache 分配发生在是否安装 Graph 的判断之前。因此，R0 eager 和原始 F1 eager 是两个不同的比较基线。[Pipeline 初始化](https://github.com/vllm-project/vllm-omni/blob/fceed074ae2f9828afa901149b2a925cf1cb0713/vllm_omni/diffusion/models/pi05/pipeline_pi05.py#L128)

实现仍包含 embedding、mask 等张量的拼接，也仍有图外 timestep 和 latent 的更新。静态 KV 只处理这里明确指出的 K/V 拼接成本。

#### 2.3 CUDA Graph：三个 region 及其数据交接

| Region | 捕获的计算 | 每请求 replay 次数 | 主要输出 |
| --- | --- | ---: | --- |
| 1 | `embed_prefix` | 1 | prefix embedding、padding/attention mask 信息 |
| 2 | prefix forward | 1 | 写入同一 KV cache 的 prefix 区域 |
| 3 | `denoise_step` | N | 本步 velocity |

模型初始化时，先 warmup，再按上述顺序捕获，使用同一 graph pool。对于一个固定部署实例，batch、相机槽数、图像分辨率、文本块长度和 action horizon 固定，所以每个 region 只需一份捕获。请求改变去噪步数时，改变的是第三段 replay 次数。

Region 1 的 embedding 输出直接作为 Region 2 的静态输入，padding mask 也可直接被 Region 3 使用；Region 2 和 3 共用同一个 KV 对象。这些连接复用了存储。但新的请求输入、prefix mask/position，以及图外更新后的 latent/timestep，仍需要填入相应静态 buffer。包装方法在传入的 Tensor 不是原静态对象时执行 `copy_`。[Graph 捕获与输入加载](https://github.com/vllm-project/vllm-omni/blob/fceed074ae2f9828afa901149b2a925cf1cb0713/vllm_omni/diffusion/models/pi05/cuda_graph_pi05.py#L76)

Graph 输出会被下一次 replay 覆盖，调用方在当前请求内及时消费；最终 action 来自图外 Euler 更新后的 latent。部署形状不匹配时，region 可以调用对应的模型函数；capture 本身失败则报错。

还要区分两种执行选择：`enforce_eager=True` 初始化的是关闭 Graph 和 fused kernels 的完整基线；某个 region 的 replay 条件不满足时，只是退回模型调用，fused kernels 是否执行仍由模型自身的开关和条件决定。[路径安装](https://github.com/vllm-project/vllm-omni/blob/fceed074ae2f9828afa901149b2a925cf1cb0713/vllm_omni/diffusion/models/pi05/pipeline_pi05.py#L249)

#### 2.4 融合 kernel：按区域和 dtype 选择

| 区域 | 当前计算选择 | 主要改变 |
| --- | --- | --- |
| Prefix | norm、residual、attention 和 GEMM 保留 torch/cuBLAS；融合 RoPE 和 `GELU × up` | 保持关键 prefix K/V 的数值行为，并减少部分逐元素操作的中间结果 |
| Denoise，BF16 action expert | Triton 实现 QKV/RoPE、attention、FFN 等组合，部分 GEMM 与后续操作融合 | 减少 kernel 边界、部分中间张量读写，并选择适合当前形状的计算实现 |
| Denoise，FP32 | GEMM 保留 cuBLAS，融合周围的逐元素计算 | 主要保留 epilogue 等局部融合收益 |

这里的 BF16 是 pipeline 的混合精度策略：vision backbone/projector 等模块仍保留 FP32。测试应记录实际布局，而不只记录一个全局 dtype 标签。[精度布局](https://github.com/vllm-project/vllm-omni/blob/fceed074ae2f9828afa901149b2a925cf1cb0713/vllm_omni/diffusion/models/pi05/pipeline_pi05.py#L86)；[prefix 与 denoise 融合实现](https://github.com/vllm-project/vllm-omni/blob/fceed074ae2f9828afa901149b2a925cf1cb0713/vllm_omni/diffusion/models/pi05/modeling_pi05.py#L1139)

### 3. 优化取舍及理由

R0 从旧实现中选择适用于当前路径的机制。下表汇总当前方案及其取舍理由。[PR 优化取舍表](https://github.com/vllm-project/vllm-omni/pull/8202)

| 候选或选择 | 当前方案 | 作者给出的理由 |
| --- | --- | --- |
| 默认执行路径 | PR 部署配置选择优化路径，显式设置 `enforce_eager` 可用完整 eager 基线 | 已提供当前结果，并保留切换入口 |
| Prefix MLP compile | 未移植 | 框架 compile 属于 R1；旧分支的 Triton prefix MLP 未优于 cuBLAS |
| Packed projections | 未移植 | 旧实现没有稳定收益，当前直接读取 `nn.Linear` 权重 |
| FP32/BF16 GEMM 后端 | BF16 action expert 使用 Triton，FP32 和 prefix 使用 cuBLAS | 作者报告本例 Triton IEEE FP32 dot 约慢 3 倍 |
| Prefix RMSNorm/attention 融合 | 关键归约保留参考路径 | 保持反复被 denoise 使用的 prefix K/V 精确一致，数值分析见第二章 |
| Decoder QKV/RoPE | 使用符合 Gemma half-split 语义的实现 | 与权重的 RoPE 布局一致 |
| 捕获边界 | 三个 region graph | 步数保持为每请求的 replay 次数；作者报告在 fused kernels 之上，Graph 额外节约 **不到 1 ms** |

### 4. 伪代码：优化具体改变了什么

以下伪代码省略 dtype 转换和形状检查，用于表达源码中的存储与执行边界。

#### 4.1 从逐步拼接 KV 到连续 cache 视图

原始拼接方式可以概括为：

```python
prefix_kv = prefill(observation)           # 每层一对 prefix K/V
for step in denoise_steps:
    for layer in layers:
        q, k_suffix, v_suffix = project_current_suffix(layer)
        k_full = cat(prefix_kv[layer].k, k_suffix)
        v_full = cat(prefix_kv[layer].v, v_suffix)
        suffix_hidden = attention(q, k_full, v_full)
        suffix_hidden = remaining_layer_ops(suffix_hidden)
```

R0 采用固定的 `[prefix | suffix]` 存储：

```python
# Pipeline 初始化：按部署形状分配一次 BS=1 cache
cache = allocate_kv(layers, 1, kv_heads, prefix_len + suffix_len, head_dim)

# 每次请求：重新计算并写入本次 observation 的 prefix K/V
prefill_into_prefix_slots(observation, cache)
for step in denoise_steps:
    for layer in layers:
        q = project_q_and_write_suffix_kv(layer, cache[layer].suffix)
        suffix_hidden = attention(q, cache[layer].k, cache[layer].v)
        suffix_hidden = remaining_layer_ops(suffix_hidden)
```

后者直接读取完整 cache 视图。普通 eager 路径仍可先计算 suffix K/V，再拷贝到槽位；融合 QKV/RoPE 路径可以直接写入 suffix 区域。两者都避免重新复制整份 prefix 来构造合并 KV。[写入接口](https://github.com/vllm-project/vllm-omni/blob/fceed074ae2f9828afa901149b2a925cf1cb0713/vllm_omni/diffusion/models/pi05/modeling_pi05.py#L298)

#### 4.2 分开初始化 capture 和每请求 replay

```python
# 初始化：启用融合计算，固定形状，完成 warmup 和 capture
enable_fused_kernels()
g_embed   = capture(embed_prefix)
g_prefix  = capture(prefix_forward_writing_cache)
g_denoise = capture(denoise_step_returning_velocity)

# 每次请求
load_request_into_static_inputs(observation)
prefix_embs, pad_mask, att_mask = g_embed.replay()
prefix_mask, positions = build_prefix_metadata(pad_mask, att_mask)
load_prefix_metadata(prefix_mask, positions)
g_prefix.replay()                         # 当前请求的 prefix K/V

x = initial_noise
dt = -1.0 / num_steps
for step in range(num_steps):
    timestep = make_device_timestep(1.0 + step * dt)  # 图外
    load_denoise_inputs(x, timestep)
    velocity = g_denoise.replay()
    x = x + dt * velocity                 # 图外 Euler 更新
return x
```

第三段图只捕获从当前 latent/timestep 到 velocity 的计算。请求有多少步，就 replay 多少次；它没有把完整循环、timestep 创建和 Euler 更新合并成一次图启动。[捕获范围](https://github.com/vllm-project/vllm-omni/blob/fceed074ae2f9828afa901149b2a925cf1cb0713/vllm_omni/diffusion/models/pi05/cuda_graph_pi05.py#L148)；[图外循环](https://github.com/vllm-project/vllm-omni/blob/fceed074ae2f9828afa901149b2a925cf1cb0713/vllm_omni/diffusion/models/pi05/modeling_pi05.py#L1796)

#### 4.3 以 BF16 action expert 的 FFN 为例

按独立算子表达的 FFN：

```python
residual = hidden
x_normed, conditioning_gate = adarmsnorm(hidden, time_condition)
gate_proj = linear(x_normed, W_gate)
up_proj   = linear(x_normed, W_up)
activated = gelu(gate_proj)
mlp_hidden = activated * up_proj
down = linear(mlp_hidden, W_down)
hidden = residual + conditioning_gate * down
```

BF16 融合路径将 projection 与后续计算合并：

```python
residual = hidden
scale, shift, conditioning_gate = split(norm_dense(time_condition))
x_normed = fused_rmsnorm_scale_shift(hidden, scale, shift)
mlp_hidden = fused_gate_up_gelu_mul(x_normed, W_gate, W_up)
hidden = fused_down_gate_residual(mlp_hidden, W_down, residual, conditioning_gate)
```

调制参数的 Linear 仍单独执行，生成的 scale/shift 交给融合 norm，gate 交给后续残差计算。FFN 前半段在一个 Triton kernel 中计算两组 projection，并完成 GELU 与乘法，减少 gate/up/activation 中间结果的独立落地。后半段把 down projection 与门控、残差相加结合起来。两段之间的 `mlp_hidden` 仍存放在全局 workspace，整个 FFN 并没有融合成一个 kernel。

FP32 路径保留 cuBLAS projection，再融合相邻逐元素计算，所以其收益结构与 BF16 不同。[FFN 融合入口](https://github.com/vllm-project/vllm-omni/blob/fceed074ae2f9828afa901149b2a925cf1cb0713/vllm_omni/diffusion/models/pi05/modeling_pi05.py#L1080)；[denoise 层调用](https://github.com/vllm-project/vllm-omni/blob/fceed074ae2f9828afa901149b2a925cf1cb0713/vllm_omni/diffusion/models/pi05/modeling_pi05.py#L1240)

### 5. 测试设计：A/B 究竟比较什么

#### 5.1 先定义各条执行路径

| 对照设计                        | 要回答的问题            | 需要保持一致的条件              |
| --------------------------- | ----------------- | ---------------------- |
| F1 eager → R0 eager         | 基础运行时组织改变后的整体差异   | 权重、精度策略、输入布局和去噪步数      |
| R0 eager → R0 fused-only    | 相同 KV 组织下，融合计算的收益 | 静态 KV 组织相同，Graph 关闭    |
| R0 fused-only → fused＋Graph | Graph 在融合之后的增量收益  | 融合 kernels 与静态 KV 组织相同 |
| R0 eager → fused＋Graph      | 完整优化组合的收益         | 相同请求、数值配置与计时边界         |

公开 CLI 通过 `enforce_eager` 选择完整 eager 基线或优化组合。若要测 fused-only、Graph-only，可复用精度测试中的模型路径切换方式，并使用相同方法计时。[路径切换参考](https://github.com/vllm-project/vllm-omni/blob/fceed074ae2f9828afa901149b2a925cf1cb0713/tests/diffusion/models/pi05/test_pi05_cuda_graph_parity.py)

#### 5.2 固定配置与计时边界

同一对 A/B 固定 GPU、权重、实际 dtype 布局、相机槽和 mask、文本长度、BS=1、action horizon、denoise 步数。先检查实际路径与 replay 次数，再使用第二章的精度测试确认结果可比较。

| 测量 | 起止边界 | 用途 |
| --- | --- | --- |
| Model-only | 已构建模型上的 `sample_actions`，调用后等待设备完成 | 比较模型调用的 wall time，排除 server 和输入预处理 |
| Client E2E | 客户端 pack → 发送 → 服务端执行 → 接收 → unpack | 衡量一次完整服务往返 |
| Per-region | `sample_actions` 内各区域的 CUDA-event 计时 | 定位耗时集中在哪一段 |

Model-only 脚本自己构建模型；E2E 脚本连接已有 server。前者的执行参数传给 benchmark，后者的执行参数传给 server。加载、启动 capture 和 warmup 不计入下面的稳态延迟。[Model benchmark](https://github.com/vllm-project/vllm-omni/blob/fceed074ae2f9828afa901149b2a925cf1cb0713/benchmarks/pi05/bench_pi05.py#L98)；[E2E 计时边界](https://github.com/vllm-project/vllm-omni/blob/fceed074ae2f9828afa901149b2a925cf1cb0713/benchmarks/pi05/e2e_latency_pi05.py#L110)

报告 p50/p95、重复次数和显存口径。E2E 脚本通过设备采样记录显存，model 脚本记录 PyTorch allocated 峰值。各组数据分别标明计时边界和配置，区域计时用于解释热点。

#### 5.3 测量顺序与重复

复测时交错运行 A/B 并重复，每轮完成相同的 warmup。保留原始样本、各轮 p50/p95 和波动范围，用来判断耗时变化是否稳定；需要归因时，按 5.1 的对照设计一次切换一个机制。

### 6. 性能结果与收益来源

设备为独占 **RTX 5080 16 GB**；测试 revision 为 `1208dc82`，F1 比较列为 `235c4303`。

#### 6.1 Client E2E：最终组合带来的请求收益

条件：BS=1、10 denoise steps、3 次 warmup 后测 30 次往返。每格三项依次对应 1／2／3 个输入相机视图；模型仍按部署的 3 个相机槽填充。

| dtype | 路径 | p50，1／2／3 views（ms） | p95，1／2／3 views（ms） | Device peak（GiB） |
| --- | --- | --- | --- | ---: |
| FP32 | R0 eager | 263.3 / 264.2 / 264.8 | 272.5 / 272.2 / 267.3 | 14.67 |
| FP32 | fused＋Graph | 240.5 / 241.9 / 242.4 | 243.1 / 245.9 / 243.8 | 14.95 |
| BF16 | R0 eager | 166.4 / 166.7 / 167.7 | 167.4 / 168.2 / 190.6 | 8.71 |
| BF16 | fused＋Graph | 118.0 / 118.1 / 118.2 | 118.9 / 120.1 / 119.6 | 9.07 |

以 3 views 的 p50 为例，FP32 从 264.8 降到 242.4 ms，延迟减少约 **8.5%**；BF16 从 167.7 降到 118.2 ms，减少约 **29.5%**。设备显存分别增加约 0.28 和 0.36 GiB。

1／2／3 views 的延迟接近，是因为缺失视图填充到固定相机槽，计算形状没有随有效视图数同比缩小。[Client E2E 结果](https://github.com/vllm-project/vllm-omni/pull/8202)

#### 6.2 Model-level：明确 F1、R0 eager、R0 optimized 三个基线

条件：直接调用 `sample_actions`，3 cameras、10 steps、5 次 warmup；下表为 p50。

| dtype | F1 eager（ms） | R0 eager（ms） | R0 fused＋Graph（ms） |
| --- | ---: | ---: | ---: |
| FP32 | 264.0 | 260.4 | 237.7 |
| BF16 | 173.0 | 168.3 | 114.0 |

F1 → R0 eager 的变化包含 R0 的基础执行组织，后者已经使用静态 KV。R0 eager → fused＋Graph 的差值则对应优化组合：FP32 延迟减少约 **8.7%**，BF16 约 **32.3%**。[Model-level 结果](https://github.com/vllm-project/vllm-omni/pull/8202)

#### 6.3 Per-region：收益集中在哪里

条件：1 个有效相机视图、10 steps，使用 CUDA events，20 次运行取 median。单位为 ms；该配置与上一表的 3-camera model wall-time 比较分别呈现。

| dtype | 路径 | Prefix embedding | Prefix forward | 10 denoise steps | 正文报告 total |
| --- | --- | ---: | ---: | ---: | ---: |
| FP32 | R0 eager | 50.8 | 143.4 | 60.8 | 255.0 |
| FP32 | fused＋Graph | 50.6 | 140.3 | 46.6 | 237.6 |
| BF16 | R0 eager | 50.7 | 46.1 | 64.7 | 161.5 |
| BF16 | fused＋Graph | 50.6 | 44.4 | 19.0 | 114.1 |

BF16 的最大改善出现在 denoise：从 64.7 降到 19.0 ms。Prefix embedding 几乎未变，优化后成为单个最大的耗时区域。FP32 的 prefix forward 仍占主要时间，周围计算提速后，总体收益受到这段计算的限制。

这个分区结果与实现选择相对应：当前重点优化 action expert，BF16 又采用了更多 GEMM 融合；vision 保留 FP32，prefix 主要保留 torch/cuBLAS。数据支持将 denoise 识别为主要改善区间，将 prefix 识别为优化后的主要耗时来源。[Per-region 结果与实现说明](https://github.com/vllm-project/vllm-omni/pull/8202)

## 二、数值精度：从 action 超差定位到 prefix 归约

### 1. 工作：加速一条路径时，需要保持什么

R0 同时改变了内存组织、执行方式和计算实现。这三类改变需要分别验证。

| 改变         | 工作内容                                    | 精度排查时要检查什么                                 |
| ---------- | --------------------------------------- | ------------------------------------------ |
| 静态 buffer  | 预分配 workspace 和 prefix KV，原地更新当前请求所需的数据 | 输入是否刷新、mask 是否覆盖有效区域、旧请求状态是否残留、输出是否被后续执行覆盖 |
| CUDA Graph | 捕获计算并 replay，减少逐次提交开销                   | 捕获与 replay 是否使用一致的计算路径，静态输入和状态是否正确更新       |
| 融合 kernel  | 将若干算子组合或替换为新的 kernel                    | 数学语义、累加精度、归约顺序、中间舍入和边界处理是否保持要求             |

R0 的正确性约定是：**算子和执行顺序保持不变的路径要求精确一致；改变数值顺序的优化使用明确的 dtype-specific tolerance，并验证其适用范围。** 这个约定决定了后面的对照组和测试门槛。[维护者对 R0 范围与验收的说明](https://github.com/vllm-project/vllm-omni/issues/7754#issuecomment-5728490722)。

### 2. 验证：四组对照分离 Graph 与融合计算

公开反例发生在 H100 的 mixed-BF16 路径。相对于 PR 自身的 eager 基线，优化路径的最大绝对误差为 **0.1098，超过该 PR 的 0.05 门槛**；相对 L2 误差为 **1.54%，仍低于其 2.5% 门槛**。

reviewer 在同一进程、同一个已加载模型、相同处理后输入和固定初始噪声下，比较了四条路径：

| 对照组           | Graph | Fused kernels | 公开观察       |
| ------------- | ----- | ------------- | ---------- |
| A：eager       | 关闭    | 关闭            | 比较基准       |
| B：Graph-only  | 开启    | 关闭            | 与 A 逐位一致   |
| C：fused-only  | 关闭    | 开启            | 重现超差       |
| D：fused＋Graph | 开启    | 开启            | 与 C 重现相同偏差 |

每种模式重复执行后，各自结果稳定；独立模型复现也与服务端输出一致。[原始反例与四组对照](https://github.com/vllm-project/vllm-omni/pull/8202#issuecomment-5907558483)。

这组实验支持以下判断：

- A 与 B 一致：该输入下，单独的 Graph replay 没有引入偏差。
- A 与 C 不一致：进入 fused 路径已经足以触发偏差。
- C 与 D 一致：加入 Graph 没有改变这次偏差，调查重点应移到融合计算。
- 各模式自身稳定：可以围绕一个确定性的反例比较中间结果。
### 3. 作者可能的排查过程

#### 3.1 先划定模型中的数值边界

Pi0.5 先计算当前 observation 的 prefix 表示和 K/V，再在多个 denoise step 中反复使用这些条件，逐步更新 action latent。

```text
observation → prefix 计算 → prefix K/V
                                  │
                       每个 denoise step 使用
                                  ↓
初始 latent → velocity 预测 → latent 更新 → … → 最终 action
```

因此，最终 action 偏差至少有三种待区分的来源：进入 denoise 前的 prefix 产物已不同；denoise 自身计算不同；两者的差异在后续迭代中相互影响。

第一轮中间检查应比较 prefix 输出和逐层 K/V，而不必立即导出所有层、所有步的全部张量。若差异已经出现在 prefix，就可以先收缩调查范围；若 prefix 一致，则继续检查 denoise。

#### 3.2 用交叉替换检验 prefix 是否影响最终偏差

在 prefix 产物的 dtype、布局及其他条件兼容时，可以做如下诊断。mask、position、初始 latent 等保持一致，只替换待检验的边界产物或执行路径。

| **prefix （K/V） 的来源** | Denoise 路径 | 要回答的问题                          |
| -------------------- | ---------- | ------------------------------- |
| 参考实现                 | 参考实现       | 完整基准                            |
| 参考实现                 | 优化实现       | 给优化 denoise 相同条件后，仍会超差吗？        |
| 优化实现                 | 参考实现       | 只改变 prefix 产物，偏差会传到最终 action 吗？ |
| 优化实现                 | 优化实现       | 能否重现原始组合的问题？                    |

若参考 prefix 显著降低偏差，而优化 prefix 在参考 denoise 中仍引入明显偏差，证据就更支持调查 prefix。若只有两条优化路径组合才异常，则要继续检查它们的接口或交互。

交叉替换时，诊断代码本身也可能增加 cast、改变布局或遗漏状态。因此，需要先确认边界兼容，并比较替换前后的张量；不能让诊断适配层成为新的混杂因素。

#### 3.3 区分本步新误差与之前累积的误差

连续去噪时，两条路径可能已经持有不同的 latent。此时某一步输出不同，既可能来自本步算子，也可能只是继承了不同的输入。

可以配合两种比较：

- **自由迭代比较**：两条路径从相同初始 latent 出发，各自推进，观察误差在哪一步开始出现、如何传播。
- **相同中间输入的一步比较**：取同一个 latent、timestep 和 prefix 条件，分别执行参考与优化的一步，检查本步新引入的差异。

前者反映整个模型的误差演化，后者帮助定位当前计算。只有观察到误差开始出现的区域后，才进一步细分到层和算子，减少无关数据和同步对测量的干扰。

#### 3.4 在 prefix 内检查三类归约

作者报告，prefix 的 **RMS variance、softmax sum、$P\cdot V$** 归约顺序变化会引入 BF16 action 偏差。它们分别对应以下计算：

| 位置           | 数学角色                                          | 为什么需要检查归约顺序                      |
| ------------ | --------------------------------------------- | -------------------------------- |
| RMS variance | RMSNorm 的均方统计，通常为 $m=\frac{1}{d}\sum_i x_i^2$ | 多个平方项需要累加；均方的变化会影响整行归一化结果        |
| Softmax sum  | 稳定 softmax 的归一化分母 $\sum_j \exp(s_j-\max(s))$  | 分母的变化会影响一组 attention 概率          |
| $P\cdot V$   | attention 输出 $o_j=\sum_i p_i v_{ij}$          | 概率与 value 的乘积沿序列维累加，顺序与中间精度会影响输出 |

这里沿用作者的 `RMS variance` 名称；RMSNorm 的均方统计并不是先减均值再平方的统计方差。

输入输出都是 BF16，也不能据此断言中间累加同为 BF16；应分别检查存储 dtype、累加 dtype，以及何时写回低精度。[PyTorch：Numerical accuracy](https://docs.pytorch.org/docs/main/notes/numerical_accuracy.html)。

局部比较也要使用相同输入：RMSNorm 固定同一个 $x$，softmax 固定同一组 scores，$P\cdot V$ 固定同一组 $P,V$，分别送入参考与融合实现。否则，后一个算子的输出差异可能只是上游误差的延续。

随后逐项恢复参考实现，记录局部输出、prefix K/V 和最终 action 的变化。最早观察到非零差异，并不等于已经找到超差根因；还要检查它是否超出局部约定，以及恢复该计算能否改善模型结果。某个替换使误差下降，只能支持它在该配置下有贡献；若多个改动相互作用，还需要组合对照。对已缩小的算子片段，可加入高精度计算作为辅助参照，区分“更接近 eager”与“更接近高精度结果”。

#### 3.5 为什么 prefix 的局部差异值得在模型层追踪

Prefix K/V 是同一次请求内反复使用的条件。即使 prefix 只计算一次，它的差异也会进入后续各次 velocity 预测。

用简化形式表示一步更新：

$$
v_k=f_\theta(x_k,t_k;K_p,V_p),\qquad
x_{k+1}=x_k+\Delta t_k\,v_k .
$$

其中 $\Delta t_k$ 按模型实际积分方向取值。Prefix 差异可能改变 $v_k$，进而改变下一步的 $x_{k+1}$；下一步又会在这个新输入上继续计算。

这解释了为什么局部算子误差需要放回完整模型中验证。误差可能传播、放大，也可能抵消；不能将它简单估成“单步误差乘以步数”，更不能仅凭某个算子 micro-test 通过就认定最终 action 一定通过。

### 4. 修复：保住关键中间状态，保留经过验证的优化

公开修复让 prefix 的 norm、residual add、attention，以及 Q/K/V 和 MLP GEMM 沿 eager 的 torch/cuBLAS 路径计算；prefix 保留 RoPE 与 `GELU × up` 融合，并继续使用预分配 KV、CUDA Graph 和 denoise 的融合路径。修复后的验证要求 prefix 输出和 K/V 与 eager 精确一致。[作者修复说明](https://github.com/vllm-project/vllm-omni/pull/8202#issuecomment-5992688444)；[固定版本中的 prefix 实现](https://github.com/vllm-project/vllm-omni/blob/fceed074ae2f9828afa901149b2a925cf1cb0713/vllm_omni/diffusion/models/pi05/modeling_pi05.py#L1139)。

这个选择的依据是中间状态的作用：先稳定会被后续多步使用的 prefix 条件，再保留其他已满足正确性约定的优化。它不是所有融合误差的通用修法；实际修复仍应由归约、cast、mask、布局或状态方面的证据决定。

修复还应保存原失败用例。正文不需要保留它的输入生成代码，但回归测试必须能再次构造同一个反例。

### 5. 补充测试：分别约束计算、执行与最终结果

| 验证层次 | 应固定或比较的内容 | 能约束什么 |
| --- | --- | --- |
| 单个 fused kernel | 相同输入下与参考算子比较；必要时增加高精度参照 | 局部数值行为、布局和边界处理 |
| Prefix 产物 | prefix 输出及逐层 K/V | 关键条件表示是否保持约定 |
| Graph 执行 | 相同 kernels 的 eager 与 Graph replay | replay 与静态状态组织是否改变计算结果 |
| 原失败请求 | 保存确定性反例，使用原有判定门槛 | 已知超差是否真实消失 |
| 完整模型与服务路径 | 多个请求、不同支持配置和连续执行 | 局部修复是否落实到最终 action，是否存在跨请求状态问题 |

PR 已有原失败用例回归、prefix 输出/K/V 精确比较，以及逐 kernel 误差检查。几种判据需要分开读：

- Graph 自动化测试使用 `torch.equal`，比较 **fused＋Graph 与相同 fused kernels 的 eager 执行**。这与前面人工四路实验中的 Graph-only 对照共同提供隔离证据。
- Prefix 测试分别对 prefix 输出、K、V 使用 `torch.equal`。
- 整模型优化路径对普通 eager 同时检查 relative L2 与最大绝对误差；BF16 的两项门槛分别为 0.025 和 0.05。
- 对发生归约重排的单算子，测试还对照 FP64，约束 fused 误差相对于 eager 误差的增幅。这是另一层判据，不能替代最终 action 验证。

[Graph 与整模型测试](https://github.com/vllm-project/vllm-omni/blob/fceed074ae2f9828afa901149b2a925cf1cb0713/tests/diffusion/models/pi05/test_pi05_cuda_graph_parity.py#L183)；[prefix 测试](https://github.com/vllm-project/vllm-omni/blob/fceed074ae2f9828afa901149b2a925cf1cb0713/tests/diffusion/models/pi05/test_pi05_cuda_graph_parity.py#L254)；[单算子判据](https://github.com/vllm-project/vllm-omni/blob/fceed074ae2f9828afa901149b2a925cf1cb0713/tests/diffusion/models/pi05/test_pi05_fused_kernels.py#L123)。

完整模型测试应同时观察最大绝对误差和整体相对误差。若观察局部相对误差，还要处理参考值接近零的情况；误差指标、归一化方式与接受门槛必须一起说明。

### 7. 迁移到面试题：国产卡与 NVIDIA 八卡训练如何排查数值差异

R0 提供的方法是：建立可比较的基线，隔离改变，找到最早的有效差异，再验证修复。八卡训练还增加了反向、分布式通信和优化器状态，需要在相应边界重复这个过程。

首先要把问题说清楚：差异是某个张量超差、NaN/Inf、loss 曲线异常，还是最终收敛质量下降？“一机八卡”也没有说明使用数据并行、张量并行、流水线并行还是参数/优化器分片。跨硬件位级不一致本身不足以判错，NVIDIA 结果也需要结合高精度局部参照和任务指标判断。

#### 7.1 先让两侧实验具有可比性

对齐权重、数据及其 rank 分配、预处理、实际精度策略、有效 batch、梯度累积、loss 归一化和优化器状态。随机层需要核对实际输入或随机状态，不能只比较配置中的 seed。先做同平台重复实验，了解自身的非确定性，再检查两平台之间的偏差。

这个步骤对应 R0 的同一模型、同一输入和噪声对照。若基础状态不同，后续层间比较无法可靠归因。

在模型能够单卡运行的情况下，可以先在两平台单卡上比较固定状态的一次前向、反向和参数更新，再在八卡上固定各 rank 的输入单独检查 collective，最后恢复计算通信重叠和完整训练。单卡与八卡比较必须匹配有效 batch、loss 缩放和梯度累积语义；若模型依赖 TP 或分片才能运行，则对可隔离的子模块建立局部对照，并保留必要的分布式边界。

#### 7.2 按训练边界定位第一次偏离

以下以数据并行为例；若使用 TP、PP 或分片训练，要把对应的中间通信和状态切分加入检查点。

| 最早出现差异的位置         | 下一步优先检查                                             |
| ----------------- | --------------------------------------------------- |
| 本地前向输出或 loss      | 预处理、mask/position、算子实现、融合与精度策略，按层缩小范围               |
| 前向一致，本地梯度不同       | backward 实现、AMP/loss scaling、梯度累积、loss reduction 语义 |
| 本地梯度符合约定，归约后才超差   | rank 对应关系、sum/mean 缩放、通信 dtype、归约顺序与同步依赖            |
| 归约后梯度符合约定，更新后参数不同 | 优化器状态、超参数、master weights、裁剪和融合 optimizer 路径         |

数据并行通常将梯度归约后交给各 rank 的优化器更新；实际实现可以重叠反向计算与通信，因此“本地梯度”必须在归约前的正确边界观测，不能把已经归约的 `.grad` 当成本地结果。[PyTorch DDP 设计说明](https://docs.pytorch.org/docs/main/notes/ddp.html)。

若怀疑通信，可以固定每个 rank 的输入梯度张量，单独运行 collective，并与明确的参考规约比较。这样才能区分通信/归约本身和进入通信前已存在的差异。归约顺序导致的小幅舍入变化仍需按容差与训练影响判断，不能仅凭不逐位一致认定通信错误。

若长时间训练才出现问题，可固定可重现的 checkpoint 和数据片段，逐步收缩到较短窗口，再比较单步中间量。单步定位完成后，仍要恢复实际训练配置验证收敛与稳定性。

#### 7.3 这一章应形成的诊断能力

面对新问题，应能说明：比较基线是什么、当前对照排除了什么、下一处要观测哪个张量、哪种结果会推翻自己的归因，以及修复后要保留哪个反例。

R0 的公开记录支撑了一个完整的数值修复案例；本文补出的交叉替换实验和八卡训练排查路径属于方法迁移，尚未执行。
